Your own installation

The Docker setup below starts Studio and MariaDB 11.8 on your computer. It uses your machine’s storage and compute. No cloud database account or subscription is required.

Start self-setup →
These instructions are for your own copy.

Nothing here provisions a database through the demo owner’s account. Database credentials and access tokens belong in your own installation. The self-hosted database connects to your local Studio, separately from the public demo.

STEP 01

Start Studio and MariaDB on your computer

Install and start Docker Desktop (or Docker Engine with Compose), and install Git. The software stack has no database subscription; it uses your computer’s resources. Clone the source and open its studio/ folder:

git clone https://github.com/Jatin2567/MariaDB-magics.git
cd MariaDB-magics/studio

Generate three separate random values, each at least 24 characters. If Python is available, run this command three times:

python -c "import secrets; print(secrets.token_urlsafe(32))"

Create a private file named .env in the studio/ folder. Replace each placeholder with a different generated value:

LOCAL_ROOT_PASSWORD=REPLACE_WITH_RANDOM_VALUE_1
LOCAL_DB_PASSWORD=REPLACE_WITH_RANDOM_VALUE_2
STUDIO_TOKEN=REPLACE_WITH_RANDOM_VALUE_3

Start the stack:

docker compose -f compose.live.yaml up --build -d

Open localhost:8081. Click Connection and sign in using the STUDIO_TOKEN you just generated. This is your local workspace.

The stack creates the magics database, loads the tutorial tables, and grants the app user SELECT only. MariaDB has no published network port; Studio connects over the private Docker network. Database files persist in a Docker volume between restarts.

When finished, stop the stack without deleting its data:

docker compose -f compose.live.yaml down
STEP 02

Check the tutorial data

The Docker stack loads these tables automatically when its database volume is first created:

  • studio_documents: three rows with VECTOR(3) values and a cosine vector index.
  • studio_history: a system-versioned row whose salary changes from 100000 to 125000.

In your local Studio’s SQL workspace, run the following statements one at a time:

SELECT VERSION();

SELECT VEC_DISTANCE_COSINE(
  VEC_FromText('[1,0,0]'), VEC_FromText('[1,0,0]')
) AS distance;

The expected distance is 0. To find the exact timestamp needed for the historical query:

SELECT id, salary, ROW_START, ROW_END
FROM studio_history FOR SYSTEM_TIME ALL
ORDER BY ROW_START;

Copy ROW_START from the older row, where salary is 100000. Preserve its microseconds. The app displays timestamps in the database session’s time zone.

Loading the samples into a separate database

If you use an existing MariaDB installation instead of the bundled stack, create/select a fresh schema and run the tutorial SQL once as its administrator using a SQL client. Studio accepts read-only queries; table creation and inserts belong in your admin SQL client.

Download tutorial SQL ↓

The script uses unique tutorial table names and does not delete existing data. It also prints a use_this_as_of timestamp before updating the salary.

The three numeric vectors are deliberately small examples for testing distance search. For semantic text search, generate document and query embeddings with the same model and dimensions.

STEP 03 · IN YOUR OWN STUDIO

Try vector search and time travel

Vector search

  1. Open Vector search in your local Studio.
  2. Set table to studio_documents, vector column to embedding, ID column to id, and Top K to 3.
  3. Leave search text empty. Paste [1,0,0] as the query vector.
  4. Run search. Expected ranking: IDs 1, 2, 3. ID 1 has distance 0.

Time travel

  1. Open Time travel in your local Studio.
  2. Set table to studio_history.
  3. Paste the older row’s ROW_START timestamp from Step 2, preserving microseconds, then run the query.
  4. The historical salary is 100000. Compare with SELECT * FROM studio_history in SQL workspace: the current salary is 125000.

Optional text embeddings

Pasted numeric vectors work with the default image. To enable text input in your own server, install requirements-embeddings.txt in its environment/image and allocate enough memory for the model. Set EMBED_MODEL to the model used to create your stored vectors. Alternatively, generate query embeddings on your computer and paste them into Studio. The public demo does not include a text model.

Connect your own existing MariaDB

If you already run MariaDB, configure a separate copy of Studio to use it. Community 11.8 LTS is the baseline used by the bundled stack. Native vectors require Community 11.7+ or Enterprise 11.4.5-3+; run the capability check above on your actual server.

Create a dedicated user with SELECT only on your chosen schema. Give the app neither administrator credentials nor FILE/EXECUTE privileges. Set these variables in your own Studio server’s environment:

VariableValue
STUDIO_MODElive
STUDIO_TOKENYour own random access token, at least 24 characters
DB_HOSTYour database hostname, without a URL scheme
DB_PORTYour database’s port
DB_NAMEYour schema name
DB_USERYour read-only database user
DB_PASSWORDThat user’s password
DB_SSL_CAFor a remote database, path to its trusted CA certificate bundle inside the app server/container; enables verified TLS

For a database running on your Docker Desktop host, host.docker.internal can identify the host from the Studio container. For a database in another container, use its service name on a shared Docker network. localhost inside a container means that container itself.

The base compose.yaml can run Studio against an existing database; copy .env.example to .env and fill your own connection settings. If DB_SSL_CA points to a local certificate, mount that file into the Studio container and use its container path. The all-in-one compose.live.yaml already configures the local connection automatically.

If you choose to host your own copy on a cloud provider, use your own project and resources. Configure its database firewall to allow that app server, enable verified TLS for the remote connection, and check your provider’s pricing yourself. No cloud database is provisioned by this project, and there is no database-compute allowance attached to public-demo sign-in.

Access to your own copy

No Studio signup is required. Your local installation uses the STUDIO_TOKEN you set in its private .env file. Sign in through Connection; sign out ends the browser session. The server uses an HttpOnly session cookie and does not save the token in browser storage.

Each installation has one configured database connection. Anyone you give that installation’s token can read the same data, including its historical rows. Keep your token private or share it only with intended collaborators. The public demo’s sample data is separate from your installation.

If something does not work

The public site still says “Demo workspace”

That is expected. Open localhost:8081 after starting your own stack. Self-setup does not alter the public demo or connect your database to it.

Docker is unavailable or localhost:8081 does not open

Start Docker Desktop/Engine, run the Compose command from studio/, and wait for the database health check. Inspect docker compose -f compose.live.yaml logs for errors. Check that port 8081 is available.

Cannot sign in to the local app

Use STUDIO_TOKEN from your local .env, not the database password. The token needs at least 24 characters. If you changed environment variables, rerun the Compose up command to recreate the app container.

The sample tables are missing

Initialization runs only when the database volume is empty. If you reused an existing volume, select the intended schema and initialize the samples once using an admin SQL client. Do not delete a volume containing data you need.

Unknown VECTOR type or wrong dimensions

Check the server version and native vector probe. The tutorial uses exactly three dimensions. Leave text input empty for the numeric example. Stored and query embeddings must have matching dimensions.

Time travel is empty

Use studio_history and the older row’s ROW_START from Step 2. A timestamp before the first insert has no rows. Versioning records changes only after it is enabled.

Connecting to a remote database fails

Check your hostname, port, network allowlist, read-only grants, and certificate trust. Use the correct DNS hostname for TLS verification. Keep secrets out of shared logs.
